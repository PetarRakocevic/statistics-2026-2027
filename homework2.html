Each arrow is a one-way step except the first: the seed cannot be walked back to a private key by anyone who lacks it, and nothing downstream reveals what is upstream. A wallet stores only the mnemonic; everything else is recomputed on demand.

3 The primitives

BIP-39: mnemonic and seed

Random entropy of 128 bits (12 words) up to 256 bits (24 words) is extended with a checksum, the first ENT/32 bits of its SHA-256, and cut into 11-bit groups, each indexing a 2048-word list. A 12-word phrase is 128+4 = 132 = 12×11 bits. The seed is PBKDF2-HMAC-SHA512(mnemonic, "mnemonic"+passphrase, 2048 iterations), giving 512 bits. The optional passphrase creates an entirely different wallet, so it works as a second factor. The 2048 iterations only slow down guessing of weak phrases; they add no entropy.

BIP-32: hierarchical deterministic keys

The master key and chain code come from HMAC-SHA512("Bitcoin seed", seed): the left 32 bytes are the master private key, the right 32 bytes the chain code. A child is derived with HMAC-SHA512 keyed by the parent chain code. Hardened children (index ≥ 2³¹, written with an apostrophe) use the parent private key as input, so a leaked child key plus the parent public key cannot reveal siblings. Normal children use the public key, which allows watch-only wallets to derive addresses.

BIP-44: derivation paths

The layout is m / purpose' / coin_type' / account' / change / address_index. Ethereum has coin type 60, so the first account is m/44'/60'/0'/0/0. BIP-44 is only a convention that lets different wallets recover the same accounts from one phrase.

secp256k1

The curve y² = x³ + 7 over a 256-bit prime field, with generator G. Public key Q = kG (see Homework 1). Ethereum uses it for ECDSA signatures with public-key recovery from the signature, which is why transactions do not carry the sender's public key.

Keccak-256

The 64-byte uncompressed public key (x‖y, without the 0x04 prefix) is hashed and the last 20 bytes are the address. Hashing compresses the key and adds a layer of separation between address and public key.

EIP-55

Take the lowercase hex address, hash its ASCII text with Keccak-256; for each letter a-f, uppercase it if the matching hex digit of the hash is 8 or higher. The address value is unchanged, only its capitalisation carries the checksum.

5 Historical context

1977 RSA, the first practical public-key system.
2001 SHA-2 family (including SHA-512) standardised by NIST.
2012 BIP-32 hierarchical deterministic wallets.
2013 BIP-39 mnemonic codes.
2014 BIP-44 multi-account hierarchy.
2015 SHA-3 standardised (FIPS 202), based on Keccak; Ethereum mainnet launches, already using the original Keccak.
2016 EIP-55 checksum addresses.

Two points come out of the timeline. The wallet standards (2012-2014) predate SHA-3 and so rely on SHA-2 internally, while Ethereum's address hash comes from the newer family. And Ethereum adopted Keccak before NIST finalised its changes, which created the SHA-3 vs Keccak mismatch below.

6 SHA-2/SHA-512 vs Keccak/SHA-3

SHA-2 / SHA-512Keccak / SHA-3
ConstructionMerkle-Damgard with compression functionSponge on a 1600-bit permutation
Length extensionPossible on raw SHA-2 (not on truncated variants)Not applicable to the sponge
Role in walletPBKDF2, HMAC (seed, BIP-32)Address, EIP-55

They are related in purpose, not in design. Keccak won the NIST competition (2012) and was standardised as SHA-3 with an added domain-separation suffix, so the padding byte differs (0x01 for original Keccak, 0x06 for SHA3-256). Same permutation, different outputs. Ethereum's "keccak256" is the original, so a library's sha3_256 will give a wrong address. Test vectors for the empty string: Keccak-256 = c5d24601…5d85a470, SHA3-256 = a7ffc6f8…f8434a.

7 Why not one algorithm for everything?

Each stage needs a different security property, and no single primitive provides them all. BIP-39/32/44 handle key management: backup in human-readable form and structured deterministic derivation. secp256k1 gives the algebraic key-pair relation needed for signatures, which a hash cannot (a hash has no verifiable public/private relation). Keccak-256 gives short, uniform, hard-to-invert identifiers. EIP-55 only detects typing mistakes; it is not security against attackers. Separation also limits damage: a break in one primitive does not automatically break the rest, and each component can be replaced (SHA-3 replaced SHA-2 in newer designs) without redesigning the whole.

10 Wallet experiment

I ran the pipeline in a BIP-39 derivation tool (Ian Coleman's open-source page) instead of a wallet extension, because it exposes every intermediate value: seed, root key, derivation path, public key, private key and address. I used the public test phrase from chapter 4, Ethereum as the coin, and the BIP-44 path m/44'/60'/0'/0/0. Only one input was changed between the two runs: the optional BIP-39 passphrase.

Run A: no passphrase

The seed begins 5eb00bbd… and the first address is 0x9858EfFD232B4033E47d90003D41EC34EcaEda94, identical to the test vector of chapter 4. The public key is shown in compressed form (33 bytes, prefix 02/03 plus x), while Ethereum hashes the uncompressed x‖y.

Observations and conclusion

First, the process is deterministic. The phrase without a passphrase gives the same address every time and in every tool, which is what makes a twelve-word backup sufficient to restore a wallet, and it confirms that BIP-44 is a shared convention rather than a property of one program.

Second, adding a four-letter passphrase altered every stage below the seed. Roughly half of the bits of the seed, the private key and the address changed, in line with the avalanche behaviour expected from a pseudorandom function such as PBKDF2-HMAC-SHA512 and the hash functions after it (chapter 9). The two root keys share only their first characters, which come from the fixed serialisation header (version, depth, parent fingerprint and child index) before the chain code and key begin. The two results look unrelated, so someone who holds the phrase but not the passphrase has no route to the second wallet and no way to tell that it exists. This is why the passphrase acts as a second factor, and also why forgetting it makes the funds unrecoverable.

Third, the experiment shows where each primitive sits. PBKDF2 produces the seed, HMAC-SHA512 produces the root key, secp256k1 turns the private key into the public key, Keccak-256 reduces that to the last 20 bytes, and EIP-55 only changes the capitalisation of the result. The mixed case in both addresses is the checksum, not part of the value. Every step is one-way, so no value on the screen allows recovery of the one before it.

Limit of the test: it is one pair of runs, so the roughly 50% figures are a single sample, not a statistical estimate. They agree with the expected 50% of a good pseudorandom function but do not prove it.
